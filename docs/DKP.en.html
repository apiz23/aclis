Objectives (mapped to proposal)

  1. Design an object-oriented system architecture from functional / non-functional requirements.
  2. Build a web platform centralizing village data, streamlining reporting, with an AI-assisted monitoring dashboard.
  3. Evaluate functionality, usability and effectiveness (usability testing + SUS).

How It Works (main scenarios)

  • District Admin records villages, residents & B40, leaders, and performance evaluations; reviews reports and issues district-wide.
  • Village Head submits monthly reports and logs issues for their own village only.
  • Sub-district Chief reviews (read-only) village data within their sub-district.
  • AI summarizes long reports, categorizes issues, and surfaces trends — all data protected (PII redacted before leaving to the cloud).

02Architecture

Clean three-layer separation: frontend, backend, and managed infrastructure — a strong "object-oriented system architecture" story for the thesis.

LayerResponsibility

Stack Justification (for report/thesis)

  • Separate Next.js + FastAPI — clean 3-tier separation → clear object-oriented system architecture for use-case/ERD diagrams.
  • Python backend — leaves the door open for local models (Ollama) without a language switch.
  • Supabase — solves cross-layer auth (one JWT verified by both Next.js and FastAPI) + photo storage + Postgres in one free box.
  • AI swappability — all AI calls go through AIProvider: GroqProvider (current), OllamaProvider (local), ClaudeProvider (future).

08Access Control (RBAC)

Three roles with different data scopes. Enforced at two layers: FastAPI (from the JWT claim) and RLS at the DB level. The Next.js UI only hides buttons a role cannot use (second line of defense, not the security boundary).

FunctionDistrict AdminVillage HeadSub-district Chief
View villagesAllOwn villageOwn sub-district
Add / edit villagesYes——
Record residents & B40Yes——
Submit monthly reportsYesOwn village—
Log community issuesYesOwn village—
View dashboardFullLimitedLimited
Leader evaluationsYes——
Audit logYes——

Implementation

  • Backend: role read from app_metadata.role in the JWT; unknown role → 403 (no default).
  • Tenant scope: get_user_scope() resolves allowed village/leader IDs per request, with a 60-second TTL cache (reduces 3–5 DB queries to 0 on cache hit).
  • DB: RLS enabled on all tables; auth_role() returns empty if role missing.

09AI Layer

Three AI features — scope-locked per the proposal (no full ML, no prediction).

FeatureFunction
Report summarizationCondenses monthly reports into a 2–3 sentence summary for quick review.
Automatic issue categorizationTags incoming issues (infrastructure / street-light / social) into issue.ai_category.
Trend insightsSurfaces recurring issues / late-submission patterns for the district dashboard.

Interface

class AIProvider(Protocol):
    def summarize_reports(self, reports: list[ReportText]) -> Summary: ...
    def categorize_issue(self, issue_text: str) -> Category: ...
    def detect_trends(self, records: list[Record]) -> list[Insight]: ...

Providers

  • GroqProvider — current, model llama-3.3-70b-versatile (selected via AI_PROVIDER=groq).
  • MockProvider — default (AI_PROVIDER=mock), for offline demos without an API key.
  • OllamaProvider / ClaudeProvider — future options (local / high quality).
PII Redaction (non-functional requirement) Before any text leaves the machine to a cloud AI provider, PII is stripped (IC numbers, full addresses, names where not needed). AI features operate on report/issue content and trends, not identity fields — so redaction costs nothing in quality and gives a strong privacy story for the defense.

Typography

  • Headings (font-heading): Barlow Semi Condensed, weight 600 — condensed institutional authority.
  • Body / UI (font-sans): Figtree 400/500/600/700 — legible at 13–16px in dense tables.
  • Mono (font-mono): JetBrains Mono — IDs, code, raw data only.
  • Stat & table numbers: always tabular-nums.

Shape & Components

  • --radius: 0.375rem — tighter than the shadcn default (0.5rem).
  • Borders over shadows as the primary separator — a bordered, tabular system, not floating cards.
  • Sidebar always dark navy, gold marks the active item — the one deliberate committed-color surface.
  • Charts: gold lead series, navy-teal second; muted grid lines, no 3D/gradient fills.

Design principles

  1. Data first — tables and numbers are the primary UI surface.
  2. Dignified restraint — no decoration; every element earns its place.
  3. Clear hierarchy — strong typographic contrast between heading sizes.
  4. Institutional legibility — optimized for reading table rows under office fluorescent lighting.
  5. No false friendliness — avoid glassmorphism, gradient text, left accent stripes.

Accessibility: WCAG 2.1 AA (public-sector service); text & placeholders ≥ 4.5:1 contrast; light mode only; respects prefers-reduced-motion.

Before text reaches a cloud AI provider, unnecessary IC/address/name data is stripped. With local Ollama, data never leaves the machine — redaction becomes belt-and-suspenders.

12Data Import

Do not underestimate — hardest non-AI task The main source file ID KKG UBAH BETUL .xlsx is 37MB, dirty: multiple mixed datasets (Pontian village heads + Johor Bahru evaluations + a Kulaijaya mosque registry that leaked in), one sheet per sub-district, and 95 embedded photos inside cells.
  1. Write a one-off import script (pandas + openpyxl).
  2. Identify and discard the out-of-scope Kulaijaya mosque rows.
  3. Normalize per-sub-district sheets into the relational schema.
  4. Extract 95 embedded images → upload to Supabase Storage → link to Leader.photo_url.
  5. Validate IC/format consistency; log rejects for manual review.
